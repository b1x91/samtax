## 0. 한 줄 정의

> **TAX 구성원만 들어오는 하나의 웹사이트에서, 질문은 가명으로 편하게 올리고, 답변도 가명으로 부담 없이 달고, 좋은 답변은 좋아요로 드러나며, 쌓인 Q&A와 콘텐츠는 TAX 공동 자산이 되는 사내 지식 플랫폼.**

서비스명은 **TQA (삼일회계법인 TAX Q&A)** 로 확정했다. 구성원이 전부 TAX 소속이므로 'LoS' 표현은 쓰지 않는다.

| 원칙 | 내용 |
|---|---|
| 운영 원칙 | 업무 관련 내용만 게시 · 답변은 내부 참고용 의견 · 오답은 비난이 아닌 정정 대상 · 고객 정보는 반드시 비식별화 |
| 확대 원칙 | 채널은 하나로, 프로덕트는 말머리로 구분, 기여는 좋아요·리더보드로 보이게 |

## 1. 플랫폼을 만드는 아이덴티티

설계의 모든 갈래가 이 세 가지에서 나온다. 보고 덱 4페이지와 동일하다.

### 1.1 익명은 가리는 기능이 아니라 표현하는 방식이다

숨기 위한 장치가 아니다. **내가 누구인지에 따라 같은 말이 다르게 전달되는 것을 막기 위한 표현의 방식**이다. 그래서 이름은 가리되 직급은 남긴다. 직급은 '나'이기 이전에 답변을 읽는 사람에게 근거가 되기 때문이다.

### 1.2 게시판이 아니라 업무 도구다

쉬는 공간이 아니라 업무의 영역이다. 느슨한 커뮤니티 UI가 아니라 각지고 밀도 높은 업무 화면으로 설계한다. 스크롤해도 정보가 빠르게 읽혀야 한다.

### 1.3 초기 활성화가 곧 생명이다

답변이 성패를 가른다. 첫 두 달에 **초창기 핵심 멤버의 활동과 홍보**가 없으면 이후에 어떤 기능을 붙여도 살아나지 않는다. 그래서 오픈과 동시에 핵심 멤버 그룹을 세팅하고, 질문이 올라오기 전에 TQA가 먼저 콘텐츠를 내보낸다(섹션 5.6).

## 2. 성공 조건

| 구분 | 지표 | 목표 | 비고 |
|---|---|---|---|
| 핵심 | 24시간 내 첫 답변률 | 70% 이상 | |
| 핵심 | 미답변(7일 초과) 질문 비율 | 10% 이하 | |
| 선행 | **주간 고유 답변자 수** | 인원의 3% 이상 | 단일 핵심 지표 |
| 선행 | 월간 활성 접속률 | 30% 이상 | 독립 사이트 전환으로 추가 |
| 선행 | 주간 고유 질문자 수 | 인원의 5% 이상 | |
| 품질 | 답변 중 `[근거]` 태그 비율 | 40% 이상 | |
| 축적 | FAQ 이관 누적 건수 | 분기당 20건 이상 | |
| 리스크 | 고객정보 의심 게시물 사후 삭제 | 0건 | 사전 차단으로 흡수 |

> 가장 중요한 단일 지표는 **주간 고유 답변자 수**다. 질문은 익명성만 보장되면 올라오지만 답변은 설계로 끌어내야 한다. 독립 사이트이므로 **월간 활성 접속률**이 두 번째 감시 지표다.
>
> 목표 수치는 가설이다. UAT와 오픈 첫 달 데이터로 현실적인 값으로 다시 잡는다.

## 3. 사용자와 권한

### 3.1 대상
- **TAX 소속 전 직급** (스태프 ~ 파트너). 직급별 권한 차등 없음
- 타 LoS 구성원: 열람 불가 (로그인 단계에서 차단)

### 3.2 접근통제
- 사내 SSO 인증 + **HR 조직코드 기준 자동 판정**. 수동 멤버 관리 금지
- 전출·퇴사 시 다음 동기화 시점에 접근 자동 회수. 기존 게시물은 삭제하지 않고 유지하며 핸들은 `(전출)` 상태 표기
- 겸임·파견 인원 기준은 HR 조직 데이터 구조 확인 후 확정 → **협의 12-2**

### 3.3 역할

| 역할 | 권한 | 비고 |
|---|---|---|
| 일반 사용자 | 질문·답변·댓글·좋아요·신고·구독, 마이 대시보드 | 전원 기본 |
| 프로덕트 큐레이터 | + 미답변 질문 지정 수신, FAQ 이관 제안, 말머리 정정 | 프로덕트별 1~2명 |
| 운영 간사 | + 신고 처리, 블라인드, FAQ 확정, 콘텐츠 발행, 리더보드 운영 | 1~2명 |
| 신원 열람 승인자 | 작성자 실명 열람 승인 (2인 승인 필수) | 운영 간사 + Risk/법무 각 1인 |
| 시스템 관리자 | 운영·배포. **열람 UI에서 작성자 신원 조회 불가, 사용자 가장 기능 미구현** | CCC |

> 관리자 화면은 지명된 인원에게만 열린다. 운영 간사와 프로덕트별 큐레이터는 **별도 선별이 필요**하다.

## 4. 표기 방식 (전면 개정)

### 4.1 원문에 내재돼 있던 충돌
원문은 "작성자·반응자 모두 화면상 익명 유지"(4장)와 "좋아요 최다·답변 최다 아이디 리더보드 공개"(3장)를 동시에 요구했고, 여기서 "아이디"가 사번인지 가명인지 정의되어 있지 않았다.

### 4.2 결정 — 가명 핸들 하나로 일원화, 직급은 태그로

아이디 · 실명 · 스레드 표시명을 따로 두지 않는다. **글 · 답변 · 댓글 · 리더보드 어디서나 같은 핸들 하나**로 보인다.

```
푸른고래58  [SA]      은빛여우07  [M]      검은돌고래40  [SM]      회색기러기12  [P]
```

| 계층 | 값 | 보이는 곳 |
|---|---|---|
| 실제 신원 | 사번 · 실명 | **본인에게만** (마이 대시보드) |
| 가명 핸들 + 직급 태그 | `푸른고래58 · SA` | 모든 화면 |

- **고정 가명 핸들** — 변경할 수 없다. 활동이 쌓일수록 그 핸들이 곧 평판이 된다
- **직급 태그** — 답변을 읽는 사람에게 맥락이 된다. 실명 · 소속 · 사번은 어떤 공개 화면에도 나타나지 않는다
- v0.2의 스레드 표시명(`익명1`, `익명2`) 계층은 **폐지**했다. 하나로 통일하는 쪽이 사용자에게 단순하고, 기여가 쌓이는 구조에도 맞다

> **직급 병기는 아직 확정이 아니다.** 익명성과 정보 공유 사이에서 장단이 갈리는 사안이라 파트너 판단을 요청한다(섹션 11, 결정 ①). 본 문서는 병기를 전제로 기술하되, 가리기로 결정되면 핸들만 남기고 섹션 4.3의 임계치를 완화한다.

### 4.3 재식별(de-anonymization) 방어
직급을 함께 보이면 프로덕트와의 조합으로 특정될 여지가 커지므로 다음은 **필수 구현**이다.

- 리더보드 **최소 활동 임계치**: 집계 기간 내 3건 이상 활동한 핸들만 등재
- **상위 10명만 공개**. 하위·전체 순위표 비공개
- 집계 **최소 기간 1주**, 일간 리더보드 미제공
- 리더보드는 **확정된 직전 기간** 기준 (실시간 순위 미노출)
- 특정 프로덕트×기간 조합의 활동자가 3명 이하이면 해당 조합 리더보드 미표시
- 작성 화면에 소속팀·고객명·담당자 기재 금지 안내 상시 표시

### 4.4 작성자 신원 열람 (Break-glass)
- 사유 제한: ① 신고 누적 임계 초과 건의 징계 검토 ② 고객정보 유출 의심 ③ 법무·감독기관 요청
- 절차: 운영 간사 신청 → Risk/법무 승인(**2인 승인**) → 열람
- 사유 · 대상 · 시각 · 승인자가 append-only 감사 로그에 기록되고 분기별 보고
- **이 정책은 사용자에게 공개한다.** 숨기면 발각 시 신뢰가 한 번에 붕괴한다

### 4.5 월간 부문별 인정의 집행
전면 가명이면 시상식에서 수상자를 호명할 수 없다.
- 공개 발표는 핸들로만 한다
- 수상 통지는 인앱 개인 알림으로 보내고, 수상자가 **비공개 수령(기본값)** 또는 실명 수령 중 선택
- 실명 수령을 택해도 공개 화면 표기는 핸들 유지. 포상 집행에 필요한 최소 인원만 확인하고 열람 로그에 남김
- HR 포상 절차 연계는 협의 필요 → **협의 12-3**

## 5. 정보 구조와 핵심 기능

### 5.1 말머리와 프로덕트 — 고르는 건 두 번

| 말머리 선택 | 필수 입력 | 저장 형태 |
|---|---|---|
| `[질문]` | **프로덕트 1개 필수** | 독립 질문 게시글 |
| `[답변]` | **대상 질문번호 1개 필수 연결** | 해당 질문의 답변으로 저장 + 목록에 독립 카드로도 노출 |

- 쓸 때: 말머리 하나, 프로덕트 하나만 고르면 끝. 고를 게 많아지면 쓰다가 그만둔다
- 찾을 때: 고른 프로덕트가 그대로 목록 필터이자 구독 단위이자 리더보드 단위가 된다
- 쌓일 때: 답변을 새 글로 써도 질문번호로 묶인다. 그래서 **며칠째 답이 없는 질문을 정확히 셀 수 있다**
- 집계상 `[답변]` 독립글과 답글은 동일하게 **답변 1건**

### 5.2 프로덕트 말머리
- 초기값: 세무조정 · 세무진단 · 세무조사지원 · 경정청구 · TP · 필라2 · 기타
- **하드코딩 금지.** 마스터 테이블로 관리해 운영 간사가 추가·순서변경·비활성 가능
- `기타` 비중이 20% 초과 시 분류 재설계 신호 → 운영 리포트 포함
- 2차 분류(세목·업종)는 오픈 이후 검토. 초기에 분류를 깊게 만들면 작성 이탈이 늘어난다

### 5.3 질문번호와 후속 질문
- 질문 생성 시 영구 질문번호 부여: `Q-2026-00417`. 인용 · 검색 · FAQ 이관 · `[답변]` 글 연결의 기준 키
- 후속 질문은 대댓글 형태로 계속 추가. 스레드는 2단계(답변 → 댓글)로 제한
- 질문 본문 하단에 "후속 질문" 블록을 별도 제공해 답변 스레드와 섞이지 않게 분리

### 5.4 답변 유형 태그
- 답변 작성 시 `[근거]` / `[경험]` / `[의견]` 중 **1개 필수**
- `[근거]` 선택 시 **근거 입력란 활성화**(법령·예규·판례·내부자료 중 1개 이상)
- `[의견]`은 "확실하지 않아도 답해도 된다"는 **면허**로 기능한다. UI 문구로 명시
- 모든 답변 하단 고정 문구: **"본 답변은 작성자 개인의 내부 참고용 의견이며 법인의 공식 세무의견이 아닙니다"**

### 5.5 반응 버튼

| 항목 | 규칙 |
|---|---|
| 버튼 | 질문·답변·댓글 각각에 `[좋아요]` `[신고]` |
| 좋아요 | **1인 1글 1회**, 본인 글 제외(버튼 비활성). 취소 가능, 취소 이력 보존 |
| 카운트 | 중복 제거된 고유 사용자 수 |
| 반응자 | 명단 미노출 ("12명이 좋아요") |
| 신고 | 사유 선택 필수(고객정보 포함 / 업무 무관 / 비방 / 오정보 / 기타) + 메모 |
| 신고 누적 | 임계치(권장 3건) 도달 시 **자동 블라인드 후** 운영 간사 검토 큐 |
| 예외 | **고객정보 포함 신고는 1건으로 즉시 블라인드** |

### 5.6 TQA 콘텐츠 (신설)

질문과 별도로 **TAX 트렌드 · 인더스트리 팁 · 예규 판례 동향**을 담는 영역이다. 홈 상단에 질문과 나란히 놓인다.

- 질문이 올라오기 전에 **TQA가 먼저 발행**한다. 질문하러 오는 곳이 아니라 **들러 보는 곳**으로 만드는 장치
- 운영 콘솔에서 작성 · 예약 · 노출을 관리한다 (초안 / 발행 예정 / 발행됨)
- 주간 다이제스트 메일에 그 주 콘텐츠를 함께 담아 보낸다
- 이것이 독립 사이트의 유입 문제에 대한 1번 답이다 (섹션 7.2)

### 5.7 검색·필터
- 프로덕트 말머리별 필터, 미답변만 / 답변 유형 / 기간 / 좋아요순·최신순
- 한국어 전문검색: PostgreSQL + 한국어 형태소 확장(`pg_bigm` 또는 mecab-ko) 전제. Elasticsearch는 초기 과투자
- **작성 중 유사 질문 추천**: 제목 입력 시 기존 질문 실시간 추천 → 중복 감소 + 기존 Q&A 재사용
- 검색은 헤더 중앙에 고정 노출한다 (섹션 9.3)

### 5.8 구독·알림
- 관심 프로덕트 말머리 자율 구독, 복수 선택
- 알림: ① 구독 프로덕트 신규 질문 ② 내 질문에 답변 ③ 내 답변에 댓글 ④ 내 글 블라인드 ⑤ 월간 인정 통지
- 수신 방식: 즉시 / 일간 요약 / 끄기 (기본값 **일간 요약**)
- **주간 미답변 다이제스트**: 매주 월요일 08:00, 구독 프로덕트의 미답변 Top 5 + 그 주 TQA 콘텐츠

### 5.9 공개 프로필과 마이 대시보드

| 화면 | 보는 사람 | 내용 |
|---|---|---|
| 공개 프로필 | 누구나 | 핸들 + 직급, 활동 시작일, 답변 수, 받은 좋아요, 주력 프로덕트, 최근 답변. **실명 · 소속 · 사번 없음** |
| 마이 대시보드 | 본인만 | **실명 · 사번**, 내 핸들, 내 질문·답변·받은 좋아요, 내 순위(전체), 기간별 활동 내역, 스크랩·알림 받는 질문 |

> 구현 제약: 마이 대시보드 응답은 **세션 주체 본인 데이터로만** 한정한다. 사용자 ID를 파라미터로 받는 조회 API를 만들지 않는다 — 권한 버그 하나로 전체 익명성이 무너지는 지점이다.

### 5.10 FAQ 이관
- 기준: 좋아요 N 이상 또는 큐레이터 제안 → 큐레이터 검수 → 운영 간사 확정
- 필수 메타: **작성 시점 세법 기준일**, 검수자, 적용 한계. 기준일 없는 FAQ는 자산이 아니라 부채
- 연 1회 유효성 재검토(기준일 경과 항목 자동 플래그)
- 이관 후에도 원본 Q&A는 유지하고 FAQ와 양방향 링크

## 6. 리더보드

### 6.1 집계
- 기간: **주 · 월 · 분기 · 임의 기간**
- 핸들당 집계: 질문 수 · 답변 수 · 누적 좋아요 수 · 신고 수
- 구현: **원천 이벤트 보존 + 일별 집계 테이블**, 임의 기간은 일별 합산으로 처리
- 집계 배치 1일 1회(새벽) + 리더보드 확정 스냅샷 보존

### 6.2 공개 리더보드

| # | 항목 | 설계 메모 |
|---|---|---|
| ① | 기간 내 좋아요 최다 | Top 10, 최소 활동 3건. 핸들 · 직급 · 주력 프로덕트 · 답변 수 · 받은 좋아요 |
| ② | 기간 내 답변 최다 | 단순 건수와 **"좋아요 1개 이상 받은 답변 수"를 병행 노출** |
| ③ | 미답변 · 지연 질문 목록 | 리더보드이자 작업 대기열 |
| ④ | 많이 본 Q&A | 조회수는 1인 1일 1회로 중복 제거 |

### 6.3 부작용 방지
- 상위권만 공개, 하위 순위 미공개
- 몰아주기: 핸들 A가 준 좋아요 중 특정 핸들 B 비중이 40% 초과 **+** 절대 건수 10건 초과 시 운영 플래그
- 짧은 시간 내 동일 사용자 쌍의 교차 좋아요, 동일 세션·기기 패턴 탐지
- **플래그는 자동 제재로 연결하지 않는다.** 운영 간사 수동 검토만 — 오탐 1건으로 신뢰가 끝난다
- 월간 인정은 수량 1위 외 "가장 도움된 답변" 등 정성 부문 포함

## 7. 플랫폼과 유입

### 7.1 독립 웹사이트
TQA는 **독립된 웹사이트**다. 오늘의삼일과는 별개 플랫폼으로 운영한다.

- **얻는 것** — 실명으로 움직이는 다른 사내 플랫폼과 섞이지 않는다. "여기는 TQA"라는 경계가 처음부터 분명하고, 화면 설계와 운영 규칙을 TQA에 맞게 가져갈 수 있다
- **풀어야 할 것** — 독립 사이트가 실패하는 전형적 경로는 품질이 아니라 **"안 들어옴"**이다. 질문이 있어야만 들어오는 구조로 두면 방문 빈도가 낮고, 낮은 방문은 다시 낮은 답변률로 돌아온다

### 7.2 유입 장치 4종 (MVP 범위)

| 장치 | 내용 |
|---|---|
| **TQA 콘텐츠 선발행** | TAX 트렌드 · 인더스트리 팁 · 예규 동향을 질문보다 먼저 발행한다. 콘텐츠가 곧 유입이다 |
| 주간 다이제스트 메일 | 알림이 아니라 유입 엔진으로 설계. 미답변 질문과 그 주 콘텐츠를 함께 담아 보낸다 |
| 공유 링크 | 메신저로 공유된 링크가 로그인 후 정확히 그 글로 열린다 |
| 모바일 사용 최적화 | 사용자는 이동 중은 물론 고객사에서도 언제 어디서든 질문할 수 있다. PC · Mobile 어디서든 최적화된 환경을 제공한다 |

### 7.3 온보딩
최초 로그인 시 익명 보장 범위와 열람 조건(4.4)을 1페이지로 명시한다. 무엇이 가려지고 무엇이 기록되는지를 먼저 밝히는 것이 신뢰 확보에 유리하다.

## 8. 고객정보 · 컴플라이언스

익명 게시판은 작성자가 "익명이니까 괜찮다"고 느껴 오히려 구체적인 고객 정보를 쓰게 만드는 구조적 유인이 있다. **작성 단계에서 세 겹으로 거른다.**

### 8.1 작성 화면 상시 안내
고객명 · 담당자 · 소속팀 기재 금지를 작성 화면에 항상 띄우고, 최초 작성 시 한 번 확인을 받는다.

### 8.2 제출 전 자동 탐지
- 사업자등록번호 패턴(`\d{3}-\d{2}-\d{5}`), 법인등록번호, 주민등록번호 패턴
- 이메일 · 전화번호
- 주요 고객 법인명 사전 매칭 (유지 주체 → **협의 12-4**)
- 차단이 아니라 **경고 + 재확인**이다. 오탐으로 작성을 막으면 아예 안 쓰게 된다

### 8.3 첨부는 이미지만
엑셀 · 워드 원본은 숨은 시트와 메타데이터로 고객정보가 통째로 나간다. 이미지만 허용하고 EXIF를 제거한다. → 결정 ③

### 8.4 운영에서 거르는 장치
- **고객정보 신고는 1건으로 즉시 블라인드**. 다른 신고는 누적 3건이 기준이지만 이것만 예외
- 유출 확인 시 완전 삭제 + 작성자 개별 안내 + Risk 보고
- 모든 답변 하단에 내부 참고용 의견 고정 문구
- 분기별 탐지·차단 통계 리포트

### 8.5 승인 체제 — 오늘의삼일 준용
**고객정보 정책, 게시물 보존기간, 외부 제출 요구 대응까지 오늘의삼일이 이미 승인받은 체제를 그대로 따른다.** 신규 승인 절차를 다시 밟지 않아도 되므로 일정이 크게 단축된다. v0.2에서 블로커로 분류했던 항목이 해소됐다.

## 9. 기술 · 화면 설계

### 9.1 규모 가정 (검증 필요)
사용자 1,000~1,500명 / 일 질문 10~30건 / 일 답변·댓글 50~150건 / 피크 동시접속 100명 내외

### 9.2 데이터 모델 스케치

### 9.4 디자인 방향
- **톤** — 업무 도구. 각진 폼(radius 0~4px), 하이라인 테두리, 높은 밀도
- **색** — 네이비 잉크 `#121A26` / 웜 뉴트럴 바탕 `#F5F4F0` / 액센트는 번트 오렌지 `#B8511A` 하나
- **서체** — Noto Sans KR. 숫자 · 질문번호 · 날짜는 모노(tabular)로 통일. 질문번호 표기가 이 제품의 시그니처
- **헤더** — 상단 네이비 바 중앙에 검색 필드를 고정 배치. 테두리 없이 `#1E2A3B` 배경으로 녹이고 `Ctrl K` 단축키 병기. 플레이스홀더는 "질문을 검색하거나 바로 작성하세요"
- **직급 태그** — 핸들 옆 작은 라운드 칩. 등급 배지처럼 튀지 않게 채도를 낮춰 표기

## 11. 의사결정 요청 (11-16 보고)

### ① 닉네임 일원화, 그리고 직급을 함께 보일 것인가

**닉네임 일원화는 확정 요청.** 아이디 · 실명 · 스레드 표시명을 따로 두지 않고 가명 핸들 하나로 통일한다.

남은 것은 **직급 병기 여부**이고, 한쪽으로 기울지 않게 양쪽을 그대로 올린다.

| 직급을 함께 보이면 | 직급을 가리면 | 참고 사실 |
|---|---|---|
| 직급이 답변의 맥락이자 근거가 된다 | 프로덕트와 조합한 특정 가능성이 낮아진다 | 오늘의삼일은 직급을 쓰지 **않았다** |
| 정보 공유가 목적이라면 읽는 사람의 판단 재료가 늘어난다 | 아랫직급이 답하기 부담이 줄어든다 | 블라인드 등 외부 게시판도 쓰지 않는다 |
| 같은 답변도 무게를 가늠할 수 있다 | 내용만으로 읽히는 환경이 된다 | 익명은 숨기 위함이 아니라, 누가 썼는지에 따라 같은 말이 다르게 전달되는 것을 막기 위함이다 |

### ② 리더보드 공개 범위
- **ⓐ 상위 10명만** — 권고
- ⓑ 전체 순위 공개

전체를 공개하면 하위권에 노출 부담이 생긴다. 본인 순위는 어느 쪽이든 본인에게만 전체를 보여준다. 함께 볼 것 — '답변 최다' 기준을 단순 건수로 할지, 좋아요 1개 이상 받은 답변 수를 병행할지.

### ③ 첨부파일 허용 범위
- **ⓐ 이미지만** — 권고, EXIF 제거
- ⓑ 문서 파일까지 허용
- ⓒ 전면 금지
