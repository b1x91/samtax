## 0. 한 줄 정의

> **TAX LoS 구성원만 들어오는 하나의 채널에서, 질문은 익명으로 편하게 올리고, 답변도 익명으로 부담 없이 달고, 좋은 답변은 좋아요로 드러나며, 쌓인 Q&A는 프로덕트를 넘나드는 LoS 공동 자산이 되는 사내 지식 채널.**

원문의 원칙을 그대로 설계 기준으로 승계한다.

| 원칙 | 내용 |
|---|---|
| 운영 원칙 | 업무 관련 내용만 게시 · 답변은 내부 참고용 의견 · 오답은 비난이 아닌 정정 대상 · 고객 정보는 반드시 비식별화 |
| 확대 원칙 | 채널은 하나로, 프로덕트는 말머리로 구분, 기여는 좋아요·리더보드로 보이게 |
| 참여 원칙 | 심리적 장벽 제거가 최우선 — 익명성은 기능이 아니라 제품의 전제 |

## 1. 문제 정의와 성공 조건

### 1.1 현재 추정 문제 (검증 필요)
- 질문이 프로덕트 단위 비공식 채널(메신저, 구두)에 흩어져 **재사용되지 않음**
- 실명 환경에서는 질문 자체가 "모른다는 노출"이 되어 질문이 올라오지 않음
- 답변자도 틀린 답변의 평판 리스크 때문에 답변을 피함
- 결과적으로 프로덕트 간 노하우(세무조정 ↔ 세무조사지원 ↔ TP ↔ 필라2)가 단절

### 1.2 성공 조건 (출시 6개월 기준 — 목표치는 가설, 확정 필요)

| 구분 | 지표 | 목표 |
|---|---|---|
| 핵심 | 24시간 내 첫 답변률 | 70% 이상 |
| 핵심 | 미답변(7일 초과) 질문 비율 | 10% 이하 |
| 선행 | 주간 고유 질문자 수 | LoS 인원의 5% 이상 |
| 선행 | 주간 고유 **답변자** 수 | LoS 인원의 3% 이상 |
| 선행 | **월간 활성 접속률** (별도 앱 전환으로 추가) | LoS 인원의 30% 이상 |
| 품질 | 답변 중 `[근거]` 태그 비율 | 40% 이상 |
| 축적 | FAQ 이관 누적 건수 | 분기당 20건 이상 |
| 리스크 | 고객정보 의심 게시물 사후 삭제 건수 | 0건 (사전 차단으로 흡수) |

> 가장 중요한 단일 지표는 **주간 고유 답변자 수**다. 질문은 익명성만 보장되면 올라오지만 답변은 설계로 끌어내야 하고, 이 서비스의 성패는 거기서 갈린다.
>
> 별도 앱으로 가기로 했으므로 **월간 활성 접속률**이 두 번째 감시 지표가 된다. 사내 포털 안에 있으면 지나가다 들어오지만, 별도 앱은 "일부러 들어와야" 하므로 유입이 끊기면 콘텐츠가 아무리 좋아도 죽는다 (섹션 8.4).

## 2. 사용자와 권한

### 2.1 대상
- **TAX LoS 소속 전 직급** (스태프 ~ 파트너). 직급별 권한 차등 없음 — 차등을 두면 익명성과 참여 원칙이 동시에 훼손됨
- 타 LoS 구성원: **열람 불가** (로그인 단계에서 차단)

### 2.2 접근통제
- 사내 SSO 인증 + **HR 조직코드 기준 자동 판정**. 수동 멤버 관리 금지(관리 부채 + 누락 리스크)
- 전출·퇴사 시 다음 동기화 시점에 접근 자동 회수. 단 **기존 게시물은 삭제하지 않고 유지**(지식 자산 보존), 핸들은 `(전출)` 상태 표기
- 겸임·파견 인원 기준은 HR 조직 데이터 구조 확인 후 확정 → **미결 10-6**
- SSO 방식·조직 동기화 방식 → **미결 10-1, 10-2**

### 2.3 역할

| 역할 | 권한 | 비고 |
|---|---|---|
| 일반 사용자 | 질문·답변·댓글·좋아요·신고·구독, 마이 대시보드 | LoS 전원 기본 |
| 프로덕트 큐레이터 | + 미답변 질문 지정 수신, FAQ 이관 제안, 말머리 정정 | 프로덕트별 1~2명 |
| LoS 운영 간사 | + 신고 처리, 게시물 숨김/삭제, FAQ 확정, 리더보드 운영 | 1~2명 |
| 신원 열람 승인자 | 작성자 실명 열람 승인 (2인 승인 필수) | 운영 간사 + Risk/법무 각 1인 |
| 시스템 관리자 | 운영·배포. **열람 UI에서 작성자 신원 조회 불가, 사용자 가장(impersonation) 기능 미구현** | CCC |

## 3. 익명성 설계 (확정)

### 3.1 원문에 내재돼 있던 충돌
원문은 "작성자·반응자 모두 **화면상 익명 유지**"(섹션 4)와 "좋아요 최다·답변 최다 **아이디 리더보드 공개**"(섹션 3)를 동시에 요구했고, 여기서 "아이디"가 사번/실명인지 가명인지가 정의되어 있지 않았다. 실명이면 리더보드가 신원 공개 장치가 되어 "틀릴까 봐 두렵다"는 1번 참여 장벽이 되살아나고, 완전 익명이면 보상 설계가 작동하지 않는다.

### 3.2 결정 — 전면 가명, 실명은 본인에게만

| 계층 | 값 예시 | 노출 범위 |
|---|---|---|
| ① 실제 신원 | 사번 · 실명 | **본인에게만** (마이 대시보드). 타인·리더보드·관리자 일반 화면 전부 미노출. 2인 승인 break-glass만 예외 |
| ② 영구 가명 핸들 | `푸른고래-4821` | 리더보드 · 월간 인정 · 마이 대시보드 |
| ③ 스레드 표시명 | `익명1`, `익명2` | 질문·답변·댓글 화면. 같은 스레드 안에서 동일인 식별만 가능, 스레드 밖 연결 불가 |

**확정 사항**
- **공개 화면에 실명이 등장하는 경로는 존재하지 않는다.** 리더보드 1위도 가명 핸들로 표기한다
- **실명 opt-in 공개 기능은 넣지 않는다.** "드러낼 수 있다"는 선택지 자체가 드러내지 않은 사람에게 압력이 되고, 익명 채널에서 그 압력은 참여를 깎는다
- 실명은 **마이 대시보드에서 본인에게만** 표시한다. 용도는 "이 핸들이 내 것이고 이게 내 활동"임을 본인이 확인하는 것
- 가명 핸들은 **변경 불가**(누적 신뢰 형성 목적). 단 재식별 피해 신고 시 운영 간사가 1회 교체 가능
- 마이 대시보드는 **세션 소유자 본인 데이터만** 반환. 관리자 조회·가장 기능을 구현하지 않는다

### 3.3 재식별(de-anonymization) 방어
가명 핸들만으로도 활동량이 적을 때는 특정될 수 있다. 다음은 **필수 구현**이다.

- 리더보드 **최소 활동 임계치**: 집계 기간 내 3건 이상 활동한 핸들만 등재
- **상위권만 공개** (원문 지시). 권장 Top 10, 하위·전체 순위표 비공개
- 집계 **최소 기간 1주**, 일간 리더보드 미제공
- 리더보드는 **확정된 직전 기간** 기준 (실시간 순위 미노출) → 실시간 조작 유인 제거
- 특정 프로덕트×기간 조합의 활동자가 3명 이하이면 해당 조합 리더보드 **미표시**
- 작성 화면에 소속팀·고객명·담당자 기재 금지 안내 상시 표시

### 3.4 작성자 신원 열람 (Break-glass)
- 사유 제한: ① 신고 누적 임계 초과 건의 징계 검토 ② 고객정보 유출 의심 ③ 법무·감독기관 요청
- 절차: 운영 간사 신청 → Risk/법무 승인(**2인 승인**) → 열람
- 모든 열람은 **사유·대상·시각·승인자**가 append-only 감사 로그에 기록, 분기별 보고
- 이 정책은 사용자에게 **공개**한다. 숨기면 발각 시 채널 신뢰가 한 번에 붕괴한다

> 익명 게시판의 신뢰는 "기술적으로 추적 불가능하다"가 아니라 "추적 조건이 명시되어 있고 지켜진다"에서 나온다. 절대 익명을 약속하지 말고, 조건부 익명을 정확히 약속할 것을 권고한다.

### 3.5 월간 부문별 인정의 집행 방식 (전면 가명 결정의 파생 쟁점)
원문 섹션 3은 "월간 부문별 인정"을 요구하는데, 전면 가명이면 **시상식에서 수상자를 호명할 수 없다.** 처리 방식:

- **공개 발표는 가명 핸들로만** 한다 (예: "11월 최다 답변 — `푸른고래-4821`")
- 수상 통지는 인앱 개인 알림으로 보내고, 수상자가 ① **비공개 수령**(가명 유지, 기본값) ② **실명 수령**(본인 명시 동의 시에만) 중 선택
- ②를 선택해도 **리더보드·공개 화면 표기는 가명 유지**. 실명은 포상 집행에 필요한 최소 인원(운영 간사·HR 담당)만 확인하고 열람 로그에 남긴다
- 포상이 HR 절차를 타야 하는 경우의 구체 흐름은 HR 협의 필요 → **미결 10-7**

## 4. 정보 구조와 글 유형

### 4.1 말머리 구조 (확정)

**독립 게시글은 `[질문]`만, 답변은 질문 하위 답글.** 단 원문의 `[질문]`/`[답변]` 말머리 선택 UI는 그대로 유지한다.

| 말머리 선택 | 필수 입력 | 저장 형태 |
|---|---|---|
| `[질문]` | **프로덕트 1개 필수** (원문 준수) | 독립 질문 게시글 |
| `[답변]` | **대상 질문번호 1개 필수 연결** | 해당 질문의 답변으로 저장 + 목록에 독립 카드로도 노출 |

- `[답변]`을 긴 글로 쓰고 싶은 수요(원문 의도)는 충족하면서, 데이터상으로는 항상 질문에 귀속되므로 **미답변 집계·답변률 지표가 정확**해진다
- 질문 스레드에는 해당 `[답변]` 글이 요약 카드 + 본문 링크로 자동 역참조된다
- 집계상 `[답변]` 독립글과 답글은 **동일하게 답변 1건**으로 카운트

### 4.2 프로덕트 말머리
- `[질문]` 작성 시 **1개 필수 선택** (원문 준수)
- 초기값: 세무조정 · 세무진단 · 세무조사지원 · 경정청구 · TP · 필라2 · 기타
- **하드코딩 금지.** 마스터 테이블로 관리해 운영 간사가 추가·순서변경·비활성 가능 (LoS 프로덕트 구성은 바뀐다)
- `기타` 비중이 20% 초과 시 분류 재설계 신호 → 운영 리포트 포함
- 2차 분류(세목·업종)는 Phase 3 이후 검토. MVP에서 분류를 깊게 만들면 작성 이탈이 늘어난다

### 4.3 질문번호와 후속 질문
- 질문 생성 시 **영구 질문번호** 부여: `Q-2026-00417` (연도 + 일련번호). 인용·검색·FAQ 이관·`[답변]` 글 연결의 기준 키. 삭제 시에도 번호 회수 없음
- 후속 질문: 원문대로 **대댓글 형태로 계속 추가**. 스레드는 2단계(답변 → 댓글)로 제한하고 그 아래는 평면 전개 — 무한 중첩은 모바일에서 읽을 수 없게 된다
- 질문 본문 하단에 "후속 질문" 블록을 별도 제공해 답변 스레드와 추가 질문이 섞이지 않게 분리

### 4.4 답변 유형 태그
- 답변 작성 시 `[근거]` / `[경험]` / `[의견]` 중 **1개 필수**
- `[근거]` 선택 시 **근거 입력란 활성화**(법령·예규·판례·내부자료 중 1개 이상). 원문의 "신뢰도는 근거 입력으로 보완" 구현체
- `[의견]`은 "확실하지 않아도 답해도 된다"는 **면허**로 기능한다. UI 문구로 명시: *"확신이 없어도 괜찮습니다. `[의견]`으로 남겨주세요."*
- 모든 답변 하단 고정 문구: **"본 답변은 작성자 개인의 내부 참고용 의견이며 법인의 공식 세무의견이 아닙니다."**

## 5. 핵심 기능 명세

### 5.1 반응 버튼

| 항목 | 규칙 |
|---|---|
| 버튼 | 질문·답변·댓글 각각에 `[좋아요]` `[신고]` 2개 (원문 준수) |
| 좋아요 | **1인 1글 1회**, 본인 글 제외(버튼 비활성). 취소 가능, 취소 이력 보존 |
| 카운트 | 중복 제거된 **고유 사용자 수** |
| 반응자 | 화면상 익명 — "12명이 좋아요"만 노출, 명단 미노출 |
| 신고 | 사유 선택 필수(고객정보 포함 / 업무 무관 / 비방 / 오정보 / 기타) + 메모 |
| 신고 누적 | 임계치(권장 3건, 운영 중 조정) 도달 시 **자동 블라인드 후** 운영 간사 검토 큐 |
| 오남용 | 동일인 반복·무근거 신고 패턴은 신고자 측 모니터링 대상 |

> **고객정보 포함 신고는 임계치와 무관하게 1건으로 즉시 블라인드** → 검토. 이 한 가지는 오탐 비용보다 유출 비용이 비교 불가하게 크다.

### 5.2 검색·필터
- 프로덕트 말머리별 필터 (원문 필수)
- 추가 필터: 미답변만 / 답변 유형 / 기간 / 좋아요순·최신순
- 한국어 전문검색: 조사·복합명사 때문에 기본 LIKE 검색은 실용성이 없다 → PostgreSQL + 한국어 형태소 확장(`pg_bigm` 또는 mecab-ko) 전제. Elasticsearch는 초기 규모에 과투자
- **작성 중 유사 질문 추천**: 제목 입력 시 기존 질문 실시간 추천 → 중복 감소 + 기존 Q&A 재사용 (Phase 3)

### 5.3 구독·알림
- 관심 프로덕트 말머리 **자율 구독** (원문 준수), 복수 선택
- 알림 종류: ① 구독 프로덕트 신규 질문 ② 내 질문에 답변 ③ 내 답변에 댓글 ④ 내 글 블라인드 ⑤ 월간 인정 통지(3.5)
- 수신 방식: 즉시 / 일간 요약 / 끄기 중 선택 (기본값 = **일간 요약**). 기본값을 즉시로 두면 알림 피로로 전체 구독 해제가 발생
- **주간 미답변 다이제스트** (원문 필수): 매주 월요일, 구독 프로덕트의 미답변 질문 Top N + 전체 미답변 건수 + 직전 주 우수 Q&A
- 채널: 인앱 + **사내 메일**. 별도 앱 전환으로 메일 알림의 중요도가 올라갔다 — 메일이 사실상 주 유입 경로가 된다 (섹션 8.4). 발송 경로 승인 → **미결 10-3**

### 5.4 마이 대시보드 (원문 섹션 4 + 실명 표시 결정 반영)
- **본인 실명·사번 표시 (본인에게만)** + 본인 가명 핸들
- 내가 쓴 질문·답변·댓글 목록, 받은 좋아요 수, 기간별 내 활동 조회 (원문 준수)
- 내 리더보드 순위는 **본인에게만 전체 순위** 표시 (타인에게는 상위권만 공개)
- 구현 제약: 응답은 **세션 주체 본인 데이터로만** 한정. 사용자 ID를 파라미터로 받는 조회 API를 만들지 않는다 (권한 버그 하나로 전체 익명성이 무너지는 지점)

### 5.5 FAQ 이관 (지식 축적)
- 기준: 좋아요 N 이상 **또는** 큐레이터 제안 → 큐레이터 검수 → 운영 간사 확정
- 필수 메타: **작성 시점 세법 기준일**, 검수자, 적용 한계. 세법은 바뀌므로 기준일 없는 FAQ는 위험 자산이 된다
- 연 1회 유효성 재검토 (기준일 경과 항목 자동 플래그)
- 이관 후에도 원본 Q&A는 유지하고 FAQ와 양방향 링크

## 6. 리더보드 설계 (원문 섹션 4)

### 6.1 집계 (Backend 필수 구현)
- 기간: **주 · 월 · 분기 · 임의 기간** (원문 준수)
- 핸들당 집계: 질문 수 · 답변 수 · 누적 좋아요 수 · 신고 수
- 구현: **원천 이벤트 보존 + 일별 집계 테이블**, 임의 기간은 일별 합산으로 처리 (월·분기 테이블을 따로 두면 임의 기간 요구를 못 받는다)
- 집계 배치 1일 1회(새벽) + 리더보드 확정 스냅샷 보존 (사후 분쟁 대응)
- 본인 글 반응 제외, 좋아요는 글별 1인 1회 (원문 준수)

### 6.2 공개 리더보드 (원문 4종 준수, 전부 가명 핸들 표기)

| # | 항목 | 설계 메모 |
|---|---|---|
| ① | 기간 내 좋아요 최다 핸들 | Top 10, 최소 활동 3건 |
| ② | 기간 내 답변 최다 핸들 | 건수만으로는 품질 역행 유인 → **"좋아요 1개 이상 받은 답변 수"** 병행 노출 권고 → **미결 10-4** |
| ③ | 미답변·지연 질문 목록 | 리더보드이자 **작업 대기열**. 이 화면이 실질적으로 답변률을 만든다 |
| ④ | 많이 본·좋아요 많은 Q&A | 조회수는 1인 1일 1회로 중복 제거 |

### 6.3 부작용 방지 (원문 준수 + 보강)
- 상위권만 공개, 하위 순위 미공개 (원문)
- 상호 몰아주기 모니터링 (원문) — 구체화: 핸들 A가 준 좋아요 중 특정 핸들 B 비중이 임계치(권장 40%) 초과 **+** 절대 건수 10건 초과 시 운영 플래그
- 짧은 시간 내 동일 사용자 쌍의 교차 좋아요, 동일 세션·기기 패턴 탐지
- 신고 다수 핸들은 관리자 검토 (원문)
- **플래그는 자동 제재로 연결하지 않는다.** 운영 간사 수동 검토만 — 익명 채널에서 자동 제재는 오탐 1건으로 신뢰가 끝난다
- 월간 인정(원문 섹션 3)은 수량 1위 외 **"가장 도움된 답변"** 등 정성 부문을 포함해 수량 경쟁 쏠림 분산. 집행 방식은 3.5

## 7. 고객정보·컴플라이언스 (회계법인 특수 요구)

원문 운영 원칙의 "고객 정보는 반드시 비식별화"는 이 서비스의 **최대 리스크 항목**이다. 익명 게시판은 작성자가 "익명이니까 괜찮다"고 느껴 오히려 구체적 고객 정보를 쓰게 만드는 구조적 유인이 있다.

### 7.1 사전 차단 (3중)
1. **작성 화면 상시 안내** + 최초 작성 시 1회 체크 ("고객 식별정보를 포함하지 않았습니다")
2. **제출 전 자동 탐지 경고** (차단이 아닌 경고 + 재확인):
   - 사업자등록번호 패턴(`\d{3}-\d{2}-\d{5}`), 법인등록번호, 주민등록번호 패턴
   - 이메일·전화번호
   - 주요 고객 법인명 사전 매칭 (사전 유지 주체 → **미결 10-5**)
   - "당사 고객" + 구체 금액·연도 조합 등 휴리스틱
3. **첨부파일 정책**: MVP는 **이미지만 허용(원본 문서 파일 금지)** 권고. 엑셀·워드 원본은 메타데이터·숨은 시트로 고객정보가 통째로 유출된다. 이미지도 EXIF 제거 → **미결 10-8**

### 7.2 사후 대응
- 고객정보 신고 1건 → 즉시 블라인드 → 24시간 내 검토
- 유출 확인 시 완전 삭제(소프트 삭제 아님) + 작성자 개별 안내 + Risk 보고 기준 적용
- 분기별 탐지·차단 통계 리포트

### 7.3 기록 관리
- 게시물 보존기간, 외부 제출 요구(감독기관·소송) 대응 방식은 **법무·Risk 사전 확인 필수**
- 모든 답변에 "내부 참고용 의견" 고정 문구 (4.4)
- 공식 세무의견이 필요한 사안은 게시판이 아닌 정식 자문 절차로 유도하는 안내 상시 노출

> 섹션 7은 **개발 착수 전 법무·Risk·개인정보 담당 승인이 선행되어야 하는 블로커**로 분류한다. 기능은 나중에 고칠 수 있지만 유출은 되돌릴 수 없다.

## 8. 기술 설계

### 8.1 규모 가정 (검증 필요)
- 사용자 1,000~1,500명 / 일 질문 10~30건 / 일 답변·댓글 50~150건 / 피크 동시접속 100명 내외
- → **단일 PostgreSQL + 배치 집계로 충분.** 샤딩·캐시 레이어·검색 전용 클러스터는 초기 과투자

### 8.2 데이터 모델 스케치

```
user_identity        사번, 실명, 조직코드, 상태(재직/전출). 암호화 저장
                     조회 경로: ① 본인 세션(마이 대시보드) ② 2인 승인 break-glass. 그 외 없음
user_handle          user_id(FK) 1:1, handle, created_at
                     ※ user_identity ↔ user_handle 조인은 권한 분리된 경로로만

question             q_no(Q-2026-00417), author_handle_id, product_id, title, body,
                     status(open/answered/closed/blinded), created_at, answered_at
product              code, name, sort_order, is_active          -- 말머리 마스터
answer               question_id, author_handle_id, type(근거/경험/의견), body,
                     is_standalone_post(= [답변] 독립글 여부), blinded
answer_source        answer_id, kind(법령/예규/판례/내부자료), ref   -- [근거] 입력
comment              parent_type(question/answer), parent_id, author_handle_id, body
followup_question    question_id, author_handle_id, body         -- 후속 질문 블록

reaction             target_type, target_id, actor_handle_id, kind(like),
                     UNIQUE(target_type, target_id, actor_handle_id)
report               target_type, target_id, reporter_handle_id, reason, memo, status
view_log             target_id, actor_handle_id, view_date       -- UNIQUE로 1일 1회

subscription         handle_id, product_id
notification_pref    handle_id, kind, channel(inapp/mail), mode(instant/daily/off)
daily_stat           stat_date, handle_id, questions, answers, likes_received, reports
                     -- 임의 기간은 이 테이블 합산으로 조회
leaderboard_snapshot period_type, period_start, rank, handle_id, metric, value
monthly_award        period, category, handle_id, receipt_mode(anon/real), consented_at
faq                  source_question_id, title, body, law_basis_date, reviewer_id
identity_access_log  requester, approver1, approver2, reason, target, accessed_at (append-only)
audit_log            모든 관리자 행위
```

**핵심 원칙**: `user_identity`와 콘텐츠 테이블은 `user_handle`을 경유해서만 연결한다. 애플리케이션 쿼리 경로에 사번·실명이 등장하지 않도록 레이어를 물리적으로 분리하고, 실명을 반환하는 API는 **본인 세션용 1개**로 제한한다.

### 8.3 플랫폼 — 별도 신규 앱 (확정)

별도 앱/사이트로 구축한다. 결정에 따른 작업 범위:

| 항목 | 내용 |
|---|---|
| 인증 | 사내 SSO 직접 연동 (SAML 2.0 또는 OIDC). IdP 확인 필요 → **미결 10-1** |
| 조직 데이터 | HR 조직코드 동기화로 TAX LoS 판정. SCIM / 일 1회 배치 / CSV 중 결정 → **미결 10-2** |
| 알림 발송 | 인앱 + 사내 메일. SMTP 릴레이·발신 도메인 승인 필요 → **미결 10-3** |
| 배포 환경 | 사내망 온프레미스 vs 클라우드, 망 정책·WAF·인증서 → **미결 10-9** |
| 클라이언트 | 모바일 웹 우선(반응형) + PWA. 세무 실무자는 이동 중·고객사에서 질문한다 |

**별도 앱의 이점** — 실명 플랫폼과 물리적으로 분리되어 "여기는 익명 공간"이라는 심리적 경계가 명확하다. 오늘의 삼일 내 메뉴였다면 "지금 내가 익명인지"를 매 화면에서 안내해야 했는데 그 부담이 사라진다. 설계 자유도도 크다.

**대신 유입이 최대 리스크가 된다** → 8.4

**온보딩 필수 요소**: 최초 로그인 시 익명 보장 범위와 열람 조건(3.4)을 1페이지로 명시한다. 별도 로그인 자체가 "추적된다"는 느낌을 줄 수 있으므로, 무엇이 익명이고 무엇이 기록되는지를 먼저 밝히는 것이 신뢰 확보에 유리하다.

### 8.4 유입 설계 (별도 앱 전환으로 신설)

별도 앱이 실패하는 전형적 경로는 품질이 아니라 **"안 들어옴"**이다. 다음을 Phase 1 범위에 포함할 것을 권고한다.

1. **주간 미답변 다이제스트 메일이 주 유입 엔진** — 단순 알림이 아니라 유입 채널로 설계. 메일 안에서 질문 제목 클릭 → 로그인 후 해당 글로 **딥링크** 복귀
2. **오늘의 삼일·인트라넷에 바로가기 배너 또는 위젯** 배치 협의 → **미결 10-10**
3. **공유 링크 딥링크**: 메신저로 공유된 질문 링크가 로그인 후 그 글로 정확히 복귀해야 한다. 홈으로 떨어지면 공유가 유입으로 전환되지 않는다
4. **PWA 홈 화면 추가 안내** (모바일 재방문율)
5. 마이 대시보드·리더보드를 **주간 단위 재방문 트리거**로 활용 (주간 요약 메일에 내 활동 요약 포함)

## 9. 단계별 로드맵

별도 앱 결정으로 인증·조직동기화·배포가 추가되어 Phase 0·1 기간을 상향했다.

| 단계 | 기간(안) | 범위 | 완료 조건 |
|---|---|---|---|
| **Phase 0** 확정 | **3주** | 미결사항 확정, 프로덕트 분류 확정, **법무·Risk·개인정보 승인**, SSO·HR연동·배포환경 협의, 화면 설계, 운영 조직(간사·큐레이터) 지정 | 섹션 7 승인서 + 인프라 협의 완료 |
| **Phase 1** MVP | **6~8주** | SSO·조직동기화·접근통제, 질문·답변·대댓글(익명), 말머리, 답변 유형 태그, 좋아요·신고, 검색·필터, 마이 대시보드, 관리자 신고 큐, 고객정보 사전 탐지, 딥링크·메일 발송 | 파일럿 그룹 2주 운영 |
| **Phase 2** 참여 | 3~4주 | 리더보드 4종, 집계 배치, 구독·알림, 주간 미답변 다이제스트, 어뷰징 모니터링, 월간 인정 통지 | 24h 첫 답변률 측정 시작 |
| **Phase 3** 축적 | 3~4주 | FAQ 이관 워크플로, 유사 질문 추천·중복 탐지, 운영 리포트 | FAQ 20건 이관 |
| **Phase 4** 선택 | — | 유사 Q&A 의미 검색, 답변 초안 제안, 프로덕트 분류 자동 제안 | 별도 검토 |

**파일럿 권고**: 전체 LoS 동시 오픈 전 2~3개 프로덕트로 2~4주 파일럿. 익명 채널은 초기 분위기가 굳으면 바뀌지 않으므로, 첫 2주에 큐레이터가 의도적으로 질문·답변을 채워 "답변이 달리는 곳"이라는 기준선을 만든다. 질문만 쌓이고 답변이 없는 상태로 공개되면 회복이 매우 어렵다. → **미결 10-11**

## 12. 이 기획안이 원문에 추가한 것

원문에 없었으나 빠지면 서비스가 작동하지 않는다고 판단한 항목:

1. **3계층 신원 분리와 재식별 방어** (3.2, 3.3) — 원문의 익명/리더보드 충돌 해소
2. **작성자 신원 열람 절차의 명문화·공개** (3.4)
3. **월간 인정의 가명 집행 방식** (3.5) — 전면 가명 결정의 필연적 파생 쟁점
4. **고객정보 사전 탐지·첨부파일 정책** (7장) — 회계법인 최대 리스크
5. **FAQ의 세법 기준일 관리** (5.5) — 기준일 없는 FAQ는 자산이 아니라 부채
6. **성공 지표와 핵심 단일 지표** (1.2) — 주간 고유 답변자 수, 월간 활성 접속률
7. **유입 설계** (8.4) — 별도 앱의 실패는 품질이 아니라 유입에서 온다
8. **파일럿 선행 및 초기 콘텐츠 시딩** (9장) — 익명 채널의 초기 분위기 고착 대응

**D-1 설계 메모** — "실명 opt-in 공개"를 기각한 이유: 선택지가 존재하는 것만으로도 드러내지 않은 사람에게 압력이 되고, 익명 채널에서 그 압력은 참여를 깎는다. 공개 화면에 실명이 등장하는 경로를 아예 만들지 않는 쪽이 설계·구현·운영 모두 단순하고 안전하다.

**D-3 설계 메모** — 별도 앱은 익명성 측면에서 더 깔끔하지만(실명 플랫폼과 물리적 분리) 유입이 구조적 약점이 된다. 이 기획안은 그 약점을 8.4로 명시적으로 상쇄했다. Phase 1에서 딥링크와 메일 발송을 "나중에"로 미루면 Phase 2에서 유입이 비는 사태가 발생하므로 MVP 범위에 포함했다.
